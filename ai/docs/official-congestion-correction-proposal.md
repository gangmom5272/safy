# 제안: 고밀도 장면의 공식 C·L 보정

> 이 문서의 “기본 비활성화” 내용은 도입 전 제안 당시 기록이다.
> 현재 운영에서는 YOLO·P2PNet 이중 분석과 C·L 보정이 활성화돼 있다.
> 현재 기준은 [SAFY 운영 AI 분석 최종 명세](production-ai-analysis.md)를 따른다.

## 문서 상태

- 상태: **구현 완료, 기본 비활성화.** 서버 실측 후 활성화 결정
- 관련 이슈: `S15P11A503-96`(AI 호출 배선), `S15P11A503-102`(위험도 계산),
  `S15P11A503-140`(고밀도 신호), `S15P11A503-106`(부하 측정)
- AI 측 결정 완료: 보정 도입, 게이트 적용(아래 "결정 사항" 참고)
- 백엔드 확인 필요: 원본값 DB 저장 여부, 응답 필드 사용 방식
- 현재 운영: `P2PNET_CONGESTION_CORRECTION_ENABLED=false`이므로 공식
  `personCount`, C, L은 YOLO 결과만 사용(동작 변화 없음)

## 결정 사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 보정 도입 | **도입** | 안 하면 여의도 시나리오에서 위험도 계산이 무의미하다 |
| 게이트 적용 | **적용** | 공식값 대체는 자동 위험등급을 직접 바꾸므로 보수적으로 다룬다 |
| 기본 활성화 | **비활성화** | 동시 요청 직렬화 위험이 실측되지 않았다 |
| 보정 출처 기록 | **응답에 포함** | P2PNet 실패로 YOLO 원본이 남았는지 구분해야 한다 |

게이트를 `denseScene.suspected`에는 적용하지 않고 공식값 대체에만 적용하는
것은 **영향 범위가 다르기 때문**이다.

| 대상 | 게이트 | 이유 |
|---|---|---|
| `denseScene.suspected` (진단) | 미적용 | 사람이 보고 판단하므로 놓치면 안 된다 |
| 공식 C·L 대체 | 적용 | 자동 위험등급을 직접 움직인다. 색종이 사진(실제 0명, P2PNet L=100)이 CAUTION을 자동 발동시키면 안 된다 |

즉 플래그는 그대로 나가 사람이 확인하고, 자동 등급을 움직이는 값만 보수적으로
처리한다.

## 한 줄 요약

고밀도 장면에서 YOLO의 C·L이 사용할 수 없는 수준이라 위험도 공식이 설계대로
동작하지 않는다. **위험을 올리는 방향으로만** P2PNet의 C·L을 사용하도록
보정할 것을 제안한다.

## 문제

### 1. 위험등급 예외 규칙이 발동하지 않는다

위험도 설계에는 다음 예외 규칙이 있다.

```text
L >= 80              → 최종 위험등급을 최소 CAUTION으로 설정
L >= 90 AND P >= 70  → 최종 위험등급을 최소 DANGER로 설정
```

`S15P11A503-138` 독립 홀드아웃 1,589장에서 측정한 결과, **정답 L이 80 이상인
1,272장에서 YOLO의 L은 한 번도 80을 넘지 못했다.** 즉 이 두 규칙은 공식값
기준으로 절대 발동하지 않는 죽은 조건이다.

### 2. 고밀도 장면에서 YOLO의 C·L 오차가 매우 크다

CROWDED 1,154장 기준이다.

| 지표 | YOLO 오차(MAE) | P2PNet 오차(MAE) |
|---|---:|---:|
| C (전체 시각적 혼잡도) | 44.15 | **5.55** |
| L (국소 최대 혼잡도) | 80.62 | **1.82** |

C와 L은 0~100 범위 값이다. YOLO의 L 오차 80.62는 사실상 신호가 없다는 뜻이다.

### 3. 구체적 사례

| 표본 | 실제 | YOLO | P2PNet |
|---|---|---|---|
| 광화문 집회 (`0212.jpg`) | 9,059명, L=100 | 1명, L=7.5 | 5,756명, L=100 |
| `0814.jpg` | 8,994명, L=100 | 6명, L=37.5 | 315명, L=100 |
| `0086.jpg` | 172명, L=100 | 17명, L=45.0 | 230명, L=100 |

위험도 공식이 C·L을 가중평균해 계산하므로, 이 프레임들의 위험도는 **실제보다
크게 낮게** 산출된다. 여의도 불꽃축제 같은 주 사용 시나리오가 정확히 이
구간이다.

### 4. 플래그 추가만으로는 해결되지 않는다

`S15P11A503-140`에서 `denseScene.suspected` 신호를 추가했지만, 백엔드가
받는 C·L 값 자체는 여전히 YOLO의 잘못된 값이다. "고밀도다"라는 플래그는
받지만 그 위험도를 계산할 입력이 틀려 있다.

## 제안

### 보정 규칙

```text
공식 C = YOLO의 C (기본)
공식 L = YOLO의 L (기본)

단, 다음 조건을 모두 만족하면 해당 프레임의 C·L을 P2PNet 값으로 대체한다.
  1. P2PNet 분석이 COMPLETED 상태다.
  2. P2PNet의 lowConfidenceSignal이 false다(대형 오탐 의심 아님).
  3. P2PNet의 값이 YOLO의 값보다 크다.

즉 위험을 올리는 방향으로만 대체하고, 낮추는 방향으로는 절대 사용하지 않는다.
```

`max()`를 취하는 것과 같으나, 게이트를 통과하지 못한 P2PNet 값은 후보에서
제외한다는 점이 다르다.

### 왜 이 형태인가

- **비대칭**: 어제까지 합의한 "안전 판정은 엄격하게, 위험 상향은 관대하게"
  원칙을 C·L에 적용한 것이다. P2PNet이 과소 계산한 경우에 위험도가 낮아지는
  일은 발생하지 않는다.
- **게이트 활용**: 색종이를 사람으로 오인한 사례(`0157.jpg`, 실제 0명인데
  P2PNet L=100)를 걸러낸다. 다만 게이트는 **대체 여부만** 막고
  `denseScene.suspected` 신호 자체는 막지 않는다.
- **기존 원칙과의 정합성**: 경기장 안전 가이드에서 참고한 "좋은 조건이 나쁜
  조건을 평균으로 상쇄하지 않는다"는 원칙과 같은 방향이다.
- **사람이 최종 판단**: 대체가 일어난 프레임은 그 사실을 기록해 관리자가
  근거를 확인할 수 있게 한다.

### 예상 효과

`denseScene` 신호 기준으로 측정한 값이다(정답 L>=80, 위험 1,272장 /
비위험 317장).

| 방식 | 재현율 | 놓친 위험 | 오경보 |
|---|---:|---:|---:|
| YOLO 단독 (현재) | 0.000 | 1,272건 | 0건 |
| 게이트 통과한 P2PNet으로 보정 | 0.838 | 206건 | 33건 |
| 게이트 무관하게 보정 | 0.943 | 72건 | 62건 |

보정을 적용하면 위험등급 예외 규칙이 실제로 동작하기 시작한다.

게이트를 대체 조건에 넣을지는 추가 논의가 필요하다. 넣으면 오경보가 적고
(33건), 빼면 놓침이 적다(72건). `S15P11A503-140`에서는 신호 자체에는 게이트를
쓰지 않기로 했으나, 공식값 대체는 영향 범위가 더 크므로 보수적으로 게이트를
적용하는 것도 합리적이다.

## 영향 범위

| 항목 | 영향 |
|---|---|
| AI 프레임 분석 API 응답 | P2PNet C·L을 응답에 추가해야 한다(현재 그림자 로그에만 존재) |
| 처리시간 | P2PNet을 모든 정상 프레임에서 실행해야 한다. CPU 기준 일반 680ms, 고밀도 1,726ms |
| DB | 보정 여부와 보정 전 원본값을 저장할 컬럼이 필요하다 |
| 자동 모델 전환 정책 | "공식 결과는 YOLO만"이라는 기존 결정을 수정해야 한다 |
| 그림자 운영 | P2PNet이 더 이상 순수 그림자가 아니게 된다 |

특히 **처리시간**이 중요하다. 지금은 P2PNet을 선택적으로만 실행하지만 보정을
적용하려면 매 프레임 실행해야 한다. 5초 프레임 간격에는 여유가 있으나 서버
CPU 실측(`S15P11A503-11.3`)과 동시 요청 부하(`S15P11A503-106`) 결과를 함께
확인해야 한다.

## 대안

### 대안 A: YOLO 기준으로 L 임계값을 재조정한다

`L >= 80` 대신 YOLO의 L 분포에 맞춰 낮춘다. 구현이 가장 간단하다.

문제는 YOLO의 L이 고밀도와 저밀도를 잘 구분하지 못한다는 것이다. 138번
측정에서 YOLO 인원수 임계값을 5~20으로 낮춰본 결과 정밀도가 0.52~0.65에
머물렀다. 임계값 조정만으로는 신호가 없는 문제를 해결할 수 없다.

### 대안 B: `denseScene` 플래그만 쓰고 C·L은 그대로 둔다

현재 상태다. 구현 비용이 0이고 공식값 정책을 바꾸지 않는다.

문제는 위험도 공식이 여전히 잘못된 C·L로 계산된다는 점이다. 플래그로
"고밀도 의심"만 알 수 있고 위험도 수치는 신뢰할 수 없다.

### 대안 C: 보정하지 않고 한계로 문서화한다

발표까지 시간이 부족하면 선택할 수 있다. "인지하고 있으며 이렇게 개선
가능하다"를 한계로 제시한다.

## 구현

`app/services/dense_scene_escalation.py`의 `correct_congestion_scores()`가
보정을 담당하고, `app/api/analysis.py`가 플래그가 켜진 경우에만 P2PNet을
동기 실행한 뒤 결과를 반영한다.

```dotenv
P2PNET_SHADOW_ENABLED=true
P2PNET_CONGESTION_CORRECTION_ENABLED=true
```

두 값이 모두 `true`여야 보정이 동작한다. 응답에 출처가 기록된다.

```json
{
  "visualCongestionScore": 82.3,
  "localPeakCongestionScore": 100.0,
  "congestionSource": "P2PNET_CORRECTED"
}
```

`congestionSource`는 `YOLO` 또는 `P2PNET_CORRECTED`다. P2PNet이 실패·시간
초과했거나 게이트가 막았거나 값이 더 낮으면 `YOLO`가 되며 값도 YOLO 원본이
유지된다.

C와 L은 **항목별로** 판단한다. C는 YOLO 값이 더 크고 L은 P2PNet 값이 더 큰
경우 L만 대체된다. 두 값 모두 "높을수록 위험"이므로 항목별 최댓값이 일관된다.

### 활성화 전 확인할 것

- 매 프레임 P2PNet 실행이 5초 예산에 들어오는지 (CPU 680~1,726ms)
- **동시 요청 처리**: `shadow_analysis`의 `_inference_lock`이 P2PNet 추론을
  프로세스당 하나로 직렬화한다. 동기 실행 시 동시 요청이 줄줄이 대기하므로
  `S15P11A503-106` 부하 측정이 필수다
- 컨테이너 RSS (서버 swap이 0이다)

## 백엔드에 남은 결정

1. 보정 전 YOLO 원본값을 DB에 남길지 (남기려면 ERD에 컬럼 추가)
2. `congestionSource`를 관리자 화면에 노출할지 (근거 표시용)
3. `denseScene` 신호를 AI 응답에도 포함할지 (현재는 그림자 로그에만 존재)

## AI 측에서 이미 정한 것

- 보정 도입 여부와 게이트 적용은 AI 정책 결정이라 위 "결정 사항"에서 확정했다
- 보정된 값은 같은 필드(`visualCongestionScore`,
  `localPeakCongestionScore`)에 담기므로 **백엔드 구조 변경이 필요 없다.**
  값이 더 정확해지고 `congestionSource` 필드가 추가될 뿐이다
