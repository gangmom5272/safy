# 프레임 품질 판정 기준 검증 및 보정

## 1. 문서 상태

- 품질 규칙 버전: `frame-quality-v0.3`
- 적용 범위: SAFY AI 프레임 사전 검사
- 관련 이슈: `S15P11A503-77`, `S15P11A503-154`
- 선행 이슈: `S15P11A503-35`, `S15P11A503-73`
- 상태: 공개 촬영 표본 기반 1차 보정 + 블러 측정 해상도 정규화

이 문서는 사람 탐지 전에 실행하는 프레임 품질 검사가 정상 프레임을
과도하게 거부하거나 불량 프레임을 통과시키지 않는지 검증한 결과를
기록한다.

## 2. 검사 위치

품질 검사는 YOLO 사람 탐지 전에 실행한다.

```text
이미지 입력
→ 디코딩
→ 해상도·밝기·블러 검사
→ 유효하지 않으면 INVALID_FRAME 반환
→ 유효하면 YOLO 사람 탐지 진행
```

불량 프레임에서 불필요한 GPU 추론을 실행하지 않고, 분석할 수 없는
입력과 모델 추론 실패를 구분하기 위한 단계다.

## 3. 품질 점수

### 해상도

다음 두 조건 중 하나라도 만족하지 못하면 `LOW_RESOLUTION`으로 판정한다.

```text
짧은 변 >= 240px
전체 픽셀 수 >= 320 × 240
```

### 밝기

이미지를 회색조로 변환한 뒤 전체 픽셀 평균을 밝기 점수로 사용한다.

```text
brightnessScore = grayscale pixel mean
```

판정 기준:

```text
brightnessScore < 35
→ TOO_DARK

brightnessScore > 220
→ TOO_BRIGHT
```

### 블러

회색조 이미지에 라플라시안 연산을 적용하고 분산을 블러 점수로 사용한다.

측정 전에 짧은 변을 720px로 맞춘다. 이미 720px 이하면 그대로 측정하고,
확대는 하지 않는다. 축소한 사본은 블러 측정에만 쓰고 모델에는 원본을
전달한다.

```text
measuredImage =
  shortSide(grayImage) > 720
    ? resizeToShortSide(grayImage, 720, INTER_AREA)
    : grayImage

blurScore = variance(Laplacian(measuredImage))
```

판정 기준:

```text
blurScore < 80
→ TOO_BLURRY
```

블러 점수가 낮을수록 경계와 세부 정보가 적은 이미지다.

정규화 근거는 `9. v0.3 보정`에 있다.

## 4. v0.1 기준

기존 `frame-quality-v0.1`에 해당하는 기준은 다음과 같았다.

```text
MIN_SHORT_SIDE = 240
MIN_PIXEL_COUNT = 640 × 360
MIN_BRIGHTNESS = 35
MAX_BRIGHTNESS = 220
MIN_BLUR_SCORE = 80
```

밝기와 블러 기준은 정상 표본에서 과거부가 발견되지 않았지만,
전체 픽셀 기준이 정상 프레임을 과도하게 거부하는 문제가 확인됐다.

## 6. 해상도 과거부 분석

기존 전체 픽셀 기준 `640×360`을 적용하면 ShanghaiTech Part A 정상 표본
182장 중 26장이 `LOW_RESOLUTION`으로 거부됐다.

```text
기존:
validCount = 156
invalidCount = 26
```

해당 26장의 YOLO 탐지율은 다른 표본보다 특별히 낮지 않았다.

| 그룹 | 표본 수 | 정답 총인원 | YOLO 탐지 | 탐지율 | MAE |
|---|---:|---:|---:|---:|---:|
| 기존 정상 해상도 | 156 | 73,176 | 731 | 1.00% | 464.39 |
| 기존 저해상도 | 26 | 5,686 | 81 | 1.42% | 215.58 |

ShanghaiTech Part A는 초고밀도 데이터이므로 두 그룹 모두 YOLO 탐지율이
낮다. 하지만 기존 저해상도 그룹이 해상도 때문에 특별히 더 분석
불가능하다는 근거는 확인되지 않았다.

## 7. 축소 표본 검증

기존 4명 탐지 표본인 `bus.jpg`를 같은 비율로 단계적으로 축소해
YOLO 사람 수와 confidence를 비교했다.

| 크기 | 사람 수 | confidence | 기존 판정 |
|---|---:|---|---|
| 360×480 | 4 | 0.882, 0.880, 0.857, 0.584 | LOW_RESOLUTION |
| 240×320 | 4 | 0.886, 0.885, 0.854, 0.568 | LOW_RESOLUTION |
| 200×267 | 4 | 0.881, 0.846, 0.845, 0.481 | LOW_RESOLUTION |
| 160×213 | 3 | 0.867, 0.803, 0.795 | LOW_RESOLUTION |
| 120×160 | 4 | 0.893, 0.856, 0.834, 0.328 | LOW_RESOLUTION |

`240×320`까지는 원본과 같은 4명을 유지했고 confidence도 안정적이었다.

`200×267`부터 최저 confidence가 감소했고, `160×213`에서는 한 명을
놓쳤다.

따라서 짧은 변 240px 기준은 유지하고 전체 픽셀 기준만
`320×240`으로 완화했다.

## 9. v0.3 보정

### 발견 경로

3840×2160 카메라 원본 사진을 수동 테스트하다가 발견했다. 사람 2명이
뚜렷하게 보이는 사진인데 `INVALID_FRAME`, `TOO_BLURRY`로 거부됐다.
같은 사진을 1280×720으로 축소하자 `COMPLETED`, `personCount = 2`로
정상 분석됐다.

```text
3840×2160  blurScore = 29.89   TOO_BLURRY
1280×720   blurScore = 262.21  통과
```

### 원인

`blurScore`는 인접 1픽셀 간 밝기 차이를 측정한다. 1픽셀이 실제로 몇 cm인지는
해상도에 따라 달라지므로, 같은 경계가 고해상도에서는 더 많은 픽셀에 퍼진다.
실제 선명함이 동일해도 인접 픽셀 간 차이는 줄어든다.

선명한 원본을 내용 변화 없이 확대만 하며 측정한 결과다.

| 원본 해상도 | 원본 | 2배 확대 | 4배 확대 |
|---|---:|---:|---:|
| 1300×955 | 474.7 | 44.8 | 4.5 |
| 620×349 | 206.1 | 22.4 | 3.5 |
| 660×415 | 3,912.9 | 347.7 | 28.5 |
| 900×374 | 513.0 | 50.0 | 5.7 |

2배 확대마다 약 1/10로 감소한다. `MIN_BLUR_SCORE = 80`은 v0.2 보정 당시
1024×768 이하 표본으로만 검증했으므로, 830만 화소 사진은 검증 범위를
벗어난다.

즉 지표가 판단 목적과 반대 방향으로 움직였다. 품질 검사는 "사람을 셀 수
있을 만큼 선명한가"를 판단해야 하는데, 해상도가 높아질수록 점수는
낮아졌다.

이 문제는 v0.2 문서의 한계 항목에 "라플라시안 분산은 이미지 크기와 장면의
질감에 영향을 받는다"로 이미 기록돼 있었으나 해결되지 않은 상태였다.

### 영향 범위

- 운영 파이프라인은 영향받지 않았다. 백엔드가
  `frame-width: ${LIVE_FRAME_WIDTH:1280}`으로 프레임 폭을 고정하므로
  실제 프레임은 검증 범위 안이었다.
- 카메라 원본 사진을 그대로 올리는 수동 테스트와 시연에서는 재현됐다.
- `LIVE_FRAME_WIDTH`를 올리면 모든 프레임이 조용히 `TOO_BLURRY`로
  버려지는 잠재 위험이 있었다. 실패가 드러나지 않고 분석만 사라진다.

### 변경 내용

```text
blurScore 측정 전 짧은 변 정규화 추가
BLUR_MEASUREMENT_SHORT_SIDE = 720
축소만 적용하고 확대는 하지 않는다
```

기준 크기 720px은 운영 프레임(1280×720)의 짧은 변과 같다. 따라서 현재
운영 프레임은 정규화 대상이 아니며 측정값이 변하지 않는다.

유지 내용:

- `MIN_SHORT_SIDE`, `MIN_PIXEL_COUNT`, `MIN_BRIGHTNESS`, `MAX_BRIGHTNESS`
- `MIN_BLUR_SCORE = 80`
- 품질 이슈 코드
- FastAPI 응답 필드와 타입
- 밝기 측정은 원본 해상도 그대로 사용한다. 픽셀 평균은 해상도에 따라
  달라지지 않는다.

### 해상도 불변성 검증

같은 사진을 4개 해상도로 변환해 판정을 비교했다.

| 표본 | v0.2 판정 | v0.3 판정 |
|---|---|---|
| 카메라 원본 4K 사진 | 4K만 `TOO_BLURRY`, 나머지 통과 | 4개 전부 통과 |
| ShanghaiTech 정상 | 4K만 `TOO_BLURRY`, 나머지 통과 | 4개 전부 통과 |
| ShanghaiTech 블러 경계 | 4K·1080p `TOO_BLURRY` | 4개 전부 통과 |
| 흐린 변형 | 4개 전부 `TOO_BLURRY` | 4개 전부 `TOO_BLURRY` |

v0.2에서는 같은 사진의 판정이 해상도에 따라 뒤집혔다. v0.3에서는 16개
조합 전부 일치했다.

정규화 후에도 진짜 흐린 사진은 2.5~4.3, 선명한 사진은 104~849로 기준선
80에서 충분히 떨어져 있다.

### 기존 표본 회귀 검증

v0.2 검증에 사용한 8개 표본으로 재검증했다.

```text
sampleCount = 8
matchedCount = 8
mismatchedCount = 0
```

블러 점수는 1024×768 표본에서 달라졌으나(768 > 720이므로 정규화 대상)
판정은 8개 전부 v0.2와 동일했다. 320×240과 267×200 표본은 720px 이하라
측정값이 변하지 않았다.

## 11. 복합 품질 이슈

야간 표본은 `TOO_DARK`와 `TOO_BLURRY`가 함께 발생했다.

과도하게 밝은 표본은 `TOO_BRIGHT`와 `TOO_BLURRY`가 함께 발생했다.

밝기 부족이나 과노출로 이미지 대비가 사라지면 라플라시안 분산도
낮아질 수 있다.

품질 검사는 첫 번째 문제만 반환하지 않고 발견한 모든 이슈를 반환한다.

## 12. 평가 실행 방법

모든 명령은 `ai` 디렉터리에서 가상환경을 활성화한 상태로 실행한다.

```bash
python -m scripts.evaluate_frame_quality \
  docs/frame-quality-manifest.example.csv \
  --output runs/evaluation/frame-quality-report.json
```

평가 매니페스트 필드:

```text
sample_id
scenario
image_path
expected_issues
```

여러 기대 이슈는 `|`로 구분한다.

```text
TOO_DARK|TOO_BLURRY
```

평가 결과 JSON에는 다음 정보가 포함된다.

- 기대 유효 상태
- 실제 유효 상태
- 기대 품질 이슈
- 실제 품질 이슈
- 기대 결과 일치 여부
- 이미지 너비와 높이
- 밝기 점수
- 블러 점수
- 전체 일치·불일치 건수

실제 이미지와 결과 JSON은 `runs/`에 저장하며 Git에 포함하지 않는다.

## 13. API 상태 회귀 기준

### 정상 프레임

```text
analysisStatus = COMPLETED
```

### 품질 기준을 통과하지 못한 프레임

```text
analysisStatus = INVALID_FRAME
```

### 디코딩할 수 없는 이미지

```text
analysisStatus = INVALID_FRAME
qualityIssues = ["DECODE_FAILED"]
```

### 품질 검사 또는 모델 추론 중 예외

```text
analysisStatus = FAILED
```

이번 보정에서는 기존 상태 코드, 응답 필드명과 타입을 변경하지 않는다.

## 14. 테스트 범위

다음 상황을 자동 테스트한다.

- 디코딩할 수 없는 바이트
- 기존 저해상도 프레임
- 320×240 최소 해상도 경계
- 어두운 프레임
- 과도하게 밝은 프레임
- 블러 프레임
- 정상 프레임
- 품질 규칙 버전
- 선명한 프레임이 720p·1080p·4K에서 모두 통과
- 흐린 프레임이 720p·1080p·4K에서 모두 거부
- 운영 프레임 크기(1280×720)는 정규화 없이 측정
- 720px 이하 프레임은 확대하지 않고 측정
- 밝음·어두움·블러·저해상도 변형 생성
- 매니페스트 로드
- 중복 `sample_id` 거부
- 기대 결과와 실제 결과 비교
- JSON 요약 및 디버그 점수 저장
- 평가 실행 스크립트

- ShanghaiTech는 실제 SAFY 시민 제보 데이터가 아니다.
- NIGHT, TOO_BRIGHT, BLURRY, LOW_RESOLUTION은 동일 원본의 합성 변형이다.
- 라플라시안 분산의 이미지 크기 의존성은 v0.3 정규화로 제거했으나,
  장면의 질감 의존성은 남아 있다. 질감이 단조로운 장면은 선명해도
  점수가 낮게 나올 수 있다.
- 짧은 변이 720px 미만인 프레임은 정규화하지 않고 원본 해상도에서
  측정한다. 확대는 정보를 추가하지 못하고 점수만 떨어뜨리기 때문이다.
  결과적으로 작은 프레임은 상대적으로 높은 점수를 받아 통과하는 쪽으로
  치우친다. 분석을 조용히 버리는 것보다 안전한 방향이며, 지나치게 작은
  프레임은 `LOW_RESOLUTION`이 별도로 거부한다.
- 실제 야간 촬영의 노이즈와 흔들림을 완전히 재현하지 못한다.
- 현재 기준은 얼굴이나 번호판 식별 가능 여부를 판단하지 않는다.
- 정상 표본 중 짧은 변 240px 미만인 4장은 계속 거부된다.

## 16. 재검토 조건

다음 데이터가 확보되면 임계값을 다시 검토한다.

- 실제 SAFY 시민 제보 정상 표본
- 실제 야간·역광·과노출 표본
- 흔들림과 초점 불량이 포함된 실제 촬영 표본
- 다양한 스마트폰 해상도와 압축률 표본
- 정상인데 `INVALID_FRAME`으로 거부된 운영 사례
- 불량인데 `COMPLETED`로 통과한 운영 사례

개인정보가 포함된 실제 시민 제보 원본은 Git에 포함하지 않는다.
