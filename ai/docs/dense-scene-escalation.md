# 고밀도 장면 위험 상향 신호와 게이트 역할

## 문서 상태

- 관련 이슈: `S15P11A503-140`
- 상태: AI 측 신호 구현 완료, 백엔드 위험도 반영은 `S15P11A503-102`에서 진행
- 운영 공식 모델: `YOLO:yolo11n` (변경 없음)
- 보조 모델: `P2PNet:safy-p2pnet-v2-epoch3` (`SHADOW`, 변경 없음)
- 프레임 분석 API 응답 계약: **변경 없음** (그림자 비교 로그에만 신호 추가)

## 배경: 왜 YOLO 인원수만으로는 고밀도를 판정할 수 없는가

`S15P11A503-138`의 독립 홀드아웃 1,589장에서 두 모델의 예측 인원수를
확인한 결과는 다음과 같다.

| 항목 | 값 |
|---|---:|
| 실제 고밀도(51명 이상) 표본 | 1,154장 |
| 실제 저밀도 표본 | 435장 |
| YOLO 전체 최대 예측 인원 | **27명** |
| CROWDED 1,154장의 YOLO 평균 예측 | 6.3명 |
| CROWDED 1,154장의 정답 평균 | 431.5명 |

YOLO는 홀드아웃 전체에서 **한 번도 51명에 도달하지 못했다.** 따라서
"YOLO 인원수가 임계값을 넘으면 고밀도"라는 규칙은 이 데이터에서 아무것도
탐지하지 못한다(재현율 0.000).

임계값을 낮춰 YOLO에게 유리하게 맞춰도 결과는 나아지지 않는다.

| YOLO 임계값 | 재현율 | 오경보율 | 정밀도 |
|---:|---:|---:|---:|
| 5 | 0.614 | 0.890 | 0.647 |
| 8 | 0.400 | 0.759 | 0.583 |
| 10 | 0.263 | 0.543 | 0.563 |
| 15 | 0.048 | 0.115 | 0.524 |
| 20 | 0.008 | 0.018 | 0.529 |

정밀도가 전 구간에서 0.52~0.65에 머무른다. 즉 어떤 임계값을 골라도
YOLO 인원수는 고밀도 여부를 가려내는 신호로 쓸 수 없다.

## 결정: 국소 최대 혼잡도 L을 신호로 쓰고 두 모델을 OR 조건으로 묶는다

```text
denseScene.suspected =
    (YOLO L >= 80)
    OR
    (P2PNet L >= 80)
```

YOLO는 고밀도에서 크게 놓치고 P2PNet은 저밀도에서 과대 계산하므로, 어느
한 모델의 값만으로 판정하지 않는다. 위험을 놓치지 않는 쪽을 우선해 OR
조건을 사용한다.

### 왜 인원수가 아니라 L인가

인원수는 면적 정보가 없어 위험도를 직접 결정할 수 없다. 좁은 골목의 51명과
광장의 51명은 위험도가 전혀 다르다. 프로젝트 설계에서도 인원수는 보조값으로
규정하고 위험도 공식은 C·L을 사용한다.

같은 정답 기준(정답 L >= 80, 위험 1,272장 / 비위험 317장)으로 두 신호를
비교한 결과다. 두 경우 모두 게이트를 거부권으로 쓰지 않는 방식이다.

| 예측 신호 | 재현율 | 놓친 위험 | 오경보 | 정밀도 |
|---|---:|---:|---:|---:|
| **L >= 80 (채택)** | **0.943** | **72건** | 62건 | 0.951 |
| 인원수 >= 51 | 0.863 | 174건 | 28건 | 0.975 |

L 기반이 놓치는 위험을 **174건에서 72건으로 102건 줄인다.** 오경보가
28건에서 62건으로 늘지만, 군중 밀집 현장이 주 용도인 서비스에서 놓침이
훨씬 비싸므로 이 교환을 선택했다.

인원수 조건을 L과 함께 OR로 병행하는 안도 측정했으나, 놓침이 72건에서
70건으로 2건 줄어드는 대신 오경보가 62건에서 68건으로 늘어 복잡도만
증가했다. 따라서 L 단독으로 판정한다.

### 임계값 80을 고른 이유

프로젝트 최종 위험등급 예외 규칙의 `L >= 80 → 최소 CAUTION` 기준을 그대로
사용한다. 신호가 먹이는 규칙과 같은 경계선을 쓰는 것이 의미가 분명하다.

임계값을 낮추면 재현율이 더 올라간다(L>=75에서 0.957, 놓침 55건). 다만
문서화된 기준을 벗어나므로 채택하지 않았고, 재조정이 필요하면 이 값을
먼저 검토한다.

## 결정: 저밀도 오탐 게이트는 위험 신호를 막지 않는다

`S15P11A503-140`에서 만든 `lowConfidenceSignal`(P2PNet 경계 구간 점 비율
기반 대형 오탐 의심 신호)을 위험 상향 판정의 **거부권으로 사용하지
않는다.** 신뢰도 정보로만 함께 기록한다.

### 근거 1: 서비스 성격

SAFY는 기존 안전관리 프로세스를 대체하지 않고 보조한다. 최종 판단은
사람이 한다. 따라서 확신이 낮다는 이유로 위험 신호를 감추는 것보다,
신호를 전달하고 "확신도가 낮다"는 사실을 함께 알리는 편이 옳다.

이 원칙은 위험도 설계의 데이터 신뢰도 규칙과도 일치한다.

```text
신뢰도가 낮아도 FinalRisk와 FinalRiskLevel은 변경하지 않는다.
ReviewStatus만 CONFIRM_REQUIRED로 설정한다.
```

### 근거 2: 실측 결과

홀드아웃 1,589장에서 게이트를 거부권으로 사용한 경우와 사용하지 않은
경우를 비교했다.

| 게이트 역할 | 재현율 | 놓친 위험 | 오경보 | 정밀도 |
|---|---:|---:|---:|---:|
| 거부권 사용 (임계 0.15) | 0.839 | 186건 | 37건 | 0.963 |
| 거부권 사용 (임계 0.20) | 0.897 | 119건 | 47건 | 0.957 |
| 거부권 사용 (임계 0.25) | 0.916 | 97건 | 56건 | 0.950 |
| 거부권 사용 (임계 0.30) | 0.921 | 91건 | 57건 | 0.949 |
| **거부권 미사용 (채택)** | **0.923** | **89건** | 61건 | 0.946 |

거부권을 사용하면 오경보 24건을 줄이는 대신 실제 위험 97건을 더 놓친다.
군중 밀집 현장 제보가 주 용도인 서비스에서 이 교환은 방향이 반대다.

### 근거 3: 게이트가 진짜 고밀도 장면을 막고 있었다

게이트를 거부권으로 사용했을 때 놓친 186건의 원인을 분해했다.

| 원인 | 건수 |
|---|---:|
| 게이트가 막아서 놓침 | 97건 |
| P2PNet 자체가 51명 미달 | 89건 |

게이트가 막은 97건의 실제 인원은 최소 52명, 중앙값 123명, **최대 8,994명**
이었다. 시나리오별 게이트 발동률을 보면 원인이 드러난다.

| 시나리오 | 게이트 발동률 |
|---|---:|
| EMPTY | 75.0% (3/4) |
| SPARSE | 35.0% (7/20) |
| NORMAL | 35.8% (24/67) |
| LOCAL_DENSE | 33.1% (114/344) |
| CROWDED | 10.7% (123/1,154) |

진짜 고밀도 장면에서도 게이트가 10.7% 발동한다. 매우 먼 거리의 작은
머리가 많아 경계 구간 점이 자연스럽게 늘어나기 때문이며, 이는 배경 질감을
사람으로 오인한 경우와 구별되지 않는다.

### 임계값 재사용이 문제였다

`lowConfidenceSignal`의 임계값 0.15는 `S15P11A503-140`에서 **"이 프레임이
저밀도 대형 오탐인가"**를 판정하기 위해 44장으로 튜닝한 값이다. 그 질문은
오탐이 비싸고, 위험 상향 판정은 놓침이 비싸다. 비용 구조가 반대인 두 결정에
같은 임계값을 재사용한 것이 원인이었다.

따라서 임계값을 조정해 재사용하는 대신 역할을 분리했다.

```text
denseScene.suspected      → 위험 상향 신호 (게이트 무관)
shadow.lowConfidenceSignal → 신뢰도 정보 (ReviewStatus 판단용)
```

## 구현

`app/services/dense_scene_escalation.py`가 판정을 담당하며,
`P2PNetShadowAnalysisService`가 그림자 비교 로그에 결과를 기록한다.
임계값은 이 모듈에 한 번만 정의하고 시뮬레이션 도구가 같은 값을 import해
런타임과 분석 기준이 어긋나지 않게 했다.

`app/services/escalation_simulation.py`는 신호 종류에 무관하게 동작하므로
인원수 기반 분석과 L 기반 분석이 같은 코드로 재현된다. 정답 신호와 예측
신호가 다른 종류일 때는 임계값을 따로 지정해야 한다(정답 L은 0~100,
예측 인원수는 상한 없음).

그림자 비교 로그에 추가되는 필드는 다음과 같다.

```json
{
  "denseScene": {
    "suspected": true,
    "officialSaysDense": false,
    "shadowSaysDense": true,
    "localPeakThreshold": 80.0
  }
}
```

프레임 분석 API 응답(`POST /api/v1/analyze/frame`)은 변경하지 않았다.
공식 `personCount`, C, L은 계속 YOLO 결과만 사용하며 자동 모델 전환도
비활성화 상태를 유지한다.

## 백엔드 연동 시 지켜야 할 계약

`S15P11A503-102`(위험도 계산)에서 이 신호를 사용할 때의 규칙이다.

```text
denseScene.suspected = true
→ 위험도를 상향하는 근거로 사용할 수 있다.

shadow.lowConfidenceSignal = true
→ RiskConfidence를 낮추고 ReviewStatus를 CONFIRM_REQUIRED로 설정한다.
→ denseScene.suspected를 무시하거나 위험도를 낮추는 데 사용하지 않는다.
```

즉 안전 판정은 엄격하게, 위험 상향은 관대하게 처리한다. 좋은 조건이
나쁜 조건을 평균으로 상쇄하지 않는다는 기존 설계 원칙과 같다.

AI 응답에 이 신호를 포함할지는 백엔드와 합의 후 결정한다. 현재는 그림자
로그에만 존재하므로 백엔드가 바로 사용할 수는 없다.

## 한계

- 홀드아웃의 73%(1,154/1,589)가 CROWDED이고 그 평균 정답 인원이 431.5명인
  초고밀도 데이터다. 실제 시민 제보는 이보다 밀도가 낮을 가능성이 높아
  YOLO의 성능이 여기서 특히 불리하게 나타난다.
- `lowConfidenceSignal` 임계값 0.15는 같은 홀드아웃의 44장으로 튜닝했으므로
  오경보 수치가 다소 낙관적일 수 있다.
- **정답 L이 74.3% 포화(100점)되어 있다.** 따라서 이 신호는 "위험한가"만
  판정하고 "얼마나 위험한가"는 구분하지 못한다. 저밀도(EMPTY·SPARSE·NORMAL)
  에서는 정답 L>=80이 0%, CROWDED에서는 98.3%로 갈리므로 이진 판정에는
  충분하지만, 심각도 구분에는 쓸 수 없다.
- P2PNet은 CROWDED 장면에서도 최대 6,435명을 예측한 사례가 있어, 인원수
  자체를 공식 값으로 쓸 수는 없다. 이 신호는 "고밀도 의심" 판정에만 쓴다.
- 임계값 80은 프로젝트 위험등급 예외 규칙 값을 그대로 가져온 것이며 실제
  제보 데이터로 재검증되지 않았다.
- 이 평가는 이미지 1장 단위 오프라인 시뮬레이션이며, 영상 단위 집계나
  동시 요청 부하는 포함하지 않는다.

## 미해결: 공식 C·L 자체가 고밀도에서 신뢰할 수 없다

이 신호는 "고밀도 의심" 플래그만 제공한다. 그런데 더 근본적인 문제가 남아
있다. 위험도 공식은 C와 L을 핵심 입력으로 쓰는데, 고밀도 장면에서 공식값인
YOLO의 C·L이 사실상 사용할 수 없는 수준이다.

| 지표 (CROWDED 1,154장) | YOLO 오차 | P2PNet 오차 |
|---|---:|---:|
| C (전체 혼잡도) | 44.15 | **5.55** |
| L (국소 최대 혼잡도) | 80.62 | **1.82** |

특히 **YOLO의 L은 정답 L>=80인 1,272장에서 한 번도 80을 넘지 못했다.**
따라서 위험등급 예외 규칙(`L >= 80 → 최소 CAUTION`,
`L >= 90 AND P >= 70 → 최소 DANGER`)이 공식값으로는 발동하지 않는다.

플래그를 추가해도 백엔드가 받는 C·L은 여전히 틀린 값이므로, 고밀도 장면의
위험도 계산은 잘못된 입력으로 수행된다. 이를 해결하려면 공식 C·L을 보정해야
하는데, 이는 "공식 결과는 YOLO만 사용한다"는 기존 원칙을 바꾸는 결정이므로
`S15P11A503-96`·`S15P11A503-102` 담당자와 합의가 필요하다. 제안 내용은
`docs/official-congestion-correction-proposal.md`에 정리했다.
