# SAFY 관리자 페이지 3차 UI/UX 수정 설계

## 목표와 범위

기존 관리자 전용 React 애플리케이션의 라우팅, 인증 흐름, TypeScript enum과 mock 데이터 흐름을 유지하면서 홈, 제보 목록, 제보 상세 화면을 요구된 정보 구조로 재배치한다. 사용자용 화면이나 백엔드 API 스펙은 변경하지 않고 새 라이브러리도 추가하지 않는다.

현재 저장소에는 제보 및 WebRTC용 실제 API 계층이 없으며 `src/mocks/adminMockData.ts`를 화면에서 직접 참조한다. 검토 및 처리 상태 변경 역시 서버 요청이 아니라 상세 페이지의 로컬 state 변경이다. 이번 수정은 이 동작을 보존하고, 추후 API 연결 지점을 컴포넌트의 상태 변경 함수에 한정한다.

## 공통 디자인

- 관리자 Primary 색상은 CSS 변수로 `#004AAD`, hover는 `#003B8A`, light 배경은 `#EAF2FF`를 정의한다.
- 위험·주의·정상·비활성 색상은 기존 의미 기반 변수를 유지한다.
- 주요 섹션은 `제목/액션 행`과 `콘텐츠 카드`를 분리하는 공통 구조를 사용한다.
- 오류, empty state, 사용자 행동 안내를 제외한 반복 설명 문구는 제거한다.
- 사이드바와 페이지 타이틀에서 `대시보드`는 `홈`, `제보 관리`는 `제보 목록`으로 표시하되 URL은 유지한다.
- 기존 radius, shadow, spacing의 시각적 성격을 유지하고 관리자 관련 선택자만 조정한다.

## 인증 헤더와 긴급 알림

`AdminHeader`는 검색, 느낌표 버튼, 이메일 카드, 고정 로그아웃 버튼을 제거한다. 헤더 왼쪽에는 기존 페이지 타이틀, 오른쪽 상단에는 긴급 알림 버튼과 관리자 프로필 트리거를 둔다.

현재 세션은 이메일만 저장하므로 표시명은 향후 `adminName`을 받을 수 있는 선택적 구조로 두되, 현재 데이터에서는 로그인 이메일의 `@` 앞부분을 안전한 fallback으로 사용한다. 프로필 트리거는 `관리자님` 접미사를 표시하고 클릭 시 `로그아웃 하기` 메뉴를 연다. 외부 클릭과 Escape로 닫으며 기존 `logout()`과 로그인 이동을 그대로 사용한다.

긴급 알림은 기존 `emergencyBanner`와 위험 제보 건수를 활용하는 빨간색 버튼으로 표시한다. 클릭 시 기존 데이터로 구성한 접근 가능한 모달을 열며 닫기 버튼, backdrop, Escape 닫기를 지원한다. 새로운 알림 API나 데이터를 만들지 않는다.

## 홈

홈의 첫 행은 실시간 위험도 지도와 실시간 연결로 구성한다. 두 섹션은 같은 grid row의 stretch 동작과 동일한 콘텐츠 높이를 사용한다. 지도 preview는 카드 영역을 채우고, 실시간 연결 카드 목록만 내부에서 세로 스크롤한다. 스크롤 영역에는 `scrollbar-gutter: stable`을 적용한다.

실시간 연결 제목 오른쪽의 `전체 보기`는 기존 `/monitoring`으로 이동한다. 각 연결 카드의 위험도 배지는 우측 상단에 배치하고 AI 감지 중복 설명은 제거한다. 영상 영역은 CSS `aspect-ratio`를 유지하며 데이터가 없으면 기존 의미의 empty state를 표시한다.

두 번째 행에서는 기존 배치 순서를 바꾸어 최근 위험 제보와 WebRTC 연결 대기열을 배치한다. 데이터와 연결 요청 로컬 동작은 그대로 유지한다.

## 제보 목록과 필터

필터는 입력 중인 draft와 실제 적용된 필터를 분리한다. 사용자는 검색어, 지역, 카테고리, 처리 상태를 기본 영역에서 설정하고 상세 조건에서 위험도, 시작일, 종료일, AI 분석 상태, 정렬을 설정한다. `필터 적용` 시 적용 상태를 갱신하며 `초기화`는 두 상태를 모두 초기화한다. 상세 조건 접힘 여부와 입력값은 컴포넌트가 살아 있는 동안 유지한다.

검색어는 현재 타입에 존재하는 제보 ID, 주소/장소명, AI 요약을 대상으로 한다. 제보자명은 현재 타입과 데이터에 없으므로 값이 제공되는 경우에만 검색 대상으로 포함할 수 있도록 선택적 필드를 사용한다. 지역은 현재 별도 행정구역 필드가 없으므로 기존 `location` 문자열 검색으로 구현한다.

날짜는 현재 받아온 mock 목록 안에서 비교한다. 카테고리와 상태는 기존 `ReportType`, `ReportStatus`, `RiskLevel`, `AiAnalysisStatus` 타입을 사용한다. 위험도 정렬은 기존 `riskScore`를 기준으로 한다. 목록 테이블에서는 검토 상태 컬럼만 제거하고 데이터와 상세 표시 기능은 유지한다.

## 제보 상세

페이지 상단 Breadcrumb는 `/reports` 링크인 `제보 목록`, 현재 중간 경로인 `제보 상세`, route param으로 만든 `제보 아이디 #값`으로 구성한다.

데스크톱 레이아웃은 다음 구조를 사용한다.

1. 제보 이미지 / 제보 정보 요약
2. 위험도 지표 / 제보 상태 관리 타임라인
3. AI 상황 요약 전체 너비

좁은 화면에서는 한 열로 내려간다. 제목은 카드 밖에 두고 콘텐츠만 카드에 둔다.

정보 요약은 ID·제보자명, 카테고리·초/요일 포함 제보 시간, 위험 정보·처리 정보, 전체 너비 주소 순서다. 위험 정보는 위험도, AI 분석 상태, 위험 점수를 묶고 처리 정보는 검토 상태, 처리 상태, 담당 관리자명 순서를 고정한다. 현재 데이터에 없는 제보자명과 이미지 URL은 `정보 없음`과 이미지 placeholder로 표시한다.

날짜 formatter는 `YYYY.MM.DD (요일) HH:mm:ss`를 반환한다. 입력에 초가 없으면 `00`초로 보완하며 유효하지 않은 값은 `정보 없음`을 반환한다.

## 위험도와 AI 요약

위험도 지표는 기존 4단계 `safe → caution → warning → danger`를 단일 공통 상수로 관리한다. API가 제공한 `riskLevel`을 현재 단계로 사용하고 `riskScore`를 함께 표시한다. 현재 단계만 강하게 강조하고 나머지는 흐리게 처리하므로 별도의 점수 기준 계산을 만들지 않는다.

AI 상황 요약은 위험 단계, 위험 점수, 주요 위험 지표, 요약 문장, 태그 순서로 구성한다. 현재 API 형태에 별도의 판단 근거가 없으므로 기존 `riskTags`를 주요 위험 지표와 태그에 활용한다. `aiSummary` 또는 태그가 비어 있으면 안전한 분석 결과 없음 메시지를 표시한다.

## 상태 관리 타임라인

기존 상태 관리와 처리 이력을 하나의 세로 타임라인으로 통합한다.

- 제보 접수: `reportedAt`을 공통 formatter로 표시한다.
- AI 상황 분석: 기존 `aiAnalysisStatus`, 위험 점수와 history에서 확인 가능한 분석 이력을 표시한다.
- 검토: 기존 `ReviewStatus`를 사용하고 pending일 때만 승인·반려 버튼을 노출한다.
- 처리 상태: 기존 순차 상태 변경 규칙과 `ReportStatus`를 유지하며 history와 담당 관리자를 표시한다.

승인·반려는 확인 모달에서 확인한 경우에만 로컬 상태를 변경한다. 모달은 접근 가능한 dialog 속성, 취소 및 확인 버튼, Escape 닫기를 제공한다. 변경 중 상태를 두어 중복 클릭을 막는다. 현재 실제 API가 없으므로 비동기 서버 요청을 가장하지 않으며, 추후 mutation을 연결할 함수를 한 곳에 둔다. 실제 API 연결 전에는 서버 오류를 발생시킬 수 없으므로 연결 불가 사실을 완료 보고에 명시한다.

완료, 현재, 대기, 반려/실패 단계는 각각 초록/Primary/회색/빨강 의미 색상으로 구분한다. 상태 변경 직후 정보 요약과 타임라인은 같은 state를 참조하여 동시에 갱신된다.

## 컴포넌트와 helper 경계

- `AdminSection`: 제목 및 선택적 액션과 콘텐츠 카드를 일관되게 조합한다.
- `Modal`: backdrop, Escape, 접근성 속성, 닫기 동작을 공통 제공한다.
- `StatusBadge`: 위험·검토·처리·AI 상태의 공통 tone을 표현한다.
- `RiskLevelIndicator`: 기존 4단계 위험도를 단계형 지표로 표현한다.
- 날짜 helper: 초와 요일을 포함한 관리자용 날짜 포맷을 제공한다.
- 상태 helper/constants: 위험 단계 순서와 의미 기반 badge tone 매핑을 한 곳에서 관리한다.

공통화는 이번 세 화면에서 실제로 중복되는 기능에만 적용하며 다른 관리자 페이지를 전면 재작성하지 않는다.

## 오류와 fallback

- route param과 일치하는 제보가 없으면 기존 목록 이동 empty state를 유지한다.
- 선택적 문자열과 배열은 렌더링 전에 검사한다.
- 긴 주소와 AI 문장은 `overflow-wrap`으로 줄바꿈한다.
- WebRTC 목록이 비어 있으면 `현재 실시간 연결이 없습니다`를 표시한다.
- 실제 API가 도입될 때 mutation 실패 메시지를 표시할 수 있는 오류 영역을 상태 변경 컴포넌트에 둔다.

## 검증

프로젝트에 테스트 러너가 없고 새 라이브러리를 설치하지 않는 제약이 있으므로 자동 단위 테스트 추가는 이번 범위에서 제외한다. 순수 helper는 TypeScript 타입 검사 및 빌드로 검증한다. 구현 후 존재하는 명령인 `npm run lint`와 `npm run build`를 실행한다. 별도 `typecheck` 스크립트는 없으며 `npm run build`의 `tsc -b`가 타입 검사를 수행한다.

수동 검증은 로그인 후 홈의 알림/프로필 dropdown과 닫기 동작, WebRTC 내부 스크롤과 이동, 목록 필터의 적용/초기화/접기/정렬, 상세 Breadcrumb와 fallback, 승인·반려 확인 모달 및 상태 동기화를 확인한다. 1920px, 1280px, 좁은 화면에서 겹침과 한 열 전환도 확인한다.
